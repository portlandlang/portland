# 0054 — Ordering: `<=>` is Ruby's, `Comparable` is a builtin trait, and strings order

- **Status:** Accepted (recommended and built in both oracles, 2026-09-25, under the deciding user's standing "make the case, recommend, build; course-correct after")
- **Date:** 2026-09-25
- **Issue:** [#76](https://github.com/portlandlang/portland/issues/76)

## Context

The Integer import (#23) excluded `<=>` as missing syntax, and the Array import found `sort` refused strings in one place and accepted them in another; the four comparisons were numbers-only. Those were one question: how does ordering work, and can a user's type take part? #76 offered three answers — `<=>` as Ruby's operator with `Comparable` as a trait (ADR 0028's shape); a named method (`compare_to`) answering an enum; or builtin-only ordering with structs sorted through `sort_by`.

The corpus was asked first. `ruby_research`'s `ordering` census over all 195,390 gems (July 2026 snapshot):

| Fact | Gems | % of gems |
|---|---:|---:|
| defines `<=>` | 4940 | 2.5% |
| `include Comparable` | 2907 | 1.5% |
| reads a `<=>` result as an integer | 728 | 0.4% |
| calls `sort` bare | 22036 | 11.3% |
| calls `between?` | 2456 | 1.3% |
| calls `clamp` | 1065 | 0.5% |

`<=>` bodies: 59% compute something, 38% delegate to one part's `<=>`, 3% compare an array of parts. `between?` and `clamp` are the growing ones — `clamp` from 0.0% of pre-2015 gems to 1.8% after 2020.

## Decision

1. **`<=>` is Ruby's operator, answering -1, 0, or 1.** Nearly five thousand gems define it, and 728 read its answer as an integer (`== 0`, `* -1`), so an `Ordering` enum would break a migration the corpus shows is real, to fix a convention nobody is confused by. It binds with the comparisons. Numbers order as before; strings order by canonical text (NFC, code point by code point — [ADR 0038](0038-2026-08-19-what-a-character-is.md)'s footing, so a decomposed `é` and a composed one are equal and neither is first); arrays order element by element under `<=>` alone, a shorter array first when every pair agrees. Mixed kinds refuse with the existing sentence, `cannot apply '<' to "a" and 1`.
1. **A struct orders by `def <=>(other)`.** `<=>` is the one operator a `def` may be named by; every other method name stays a word. A struct with `<=>` alone answers `<=>` and sorts — `sort`, `min`, and `max` over an array of structs call it, stably.
1. **`include Comparable` is the one builtin trait.** It carries no methods of its own: the four orderings, `between?`, and `clamp` derive from the struct's `<=>`, which must exist — `Box includes Comparable but defines no '<=>' — define it`. Without the include, `a < b` on structs says `cannot apply '<' to Box(size: 1) and Box(size: 2) — include Comparable in Box`. `Comparable` is a builtin's name under [ADR 0052](0052-2026-09-24-one-definition-per-name.md), so a user's `trait Comparable` refuses. Ruby's `include Comparable` migrates unchanged, which is the trait system's promise ([mixins-and-inheritance.md](../ruby/mixins-and-inheritance.md)).
1. **`between?` and `clamp` land on numbers and strings too**, as Ruby's `Comparable` gives them to both. A struct's `<=>` that answers anything but an integer refuses: `'<=>' answers -1, 0, or 1, got "nope"`.

### The case against, and the answer

A named method with an enum answer (option 2) is closer to ADR 0003's words-over-sigils lean and to Portland's closed vocabularies. It loses on the corpus: the operator is how thousands of Ruby types already spell their ordering, and a migrating `def <=>` would need rewriting at every definition and every call that reads the integer. Builtin-only ordering (option 3) is smaller but leaves 2.5% of gems — every version type, every money type — with no port.

## Consequences

- The seed gains a `Spaceship` token and operator, a `comparable` flag on each struct, and struct-aware `sort`/`min`/`max`; the trio mirrors each, and inference types `<=>` as an integer on numbers, strings, and arrays.
- The checker accepts strings under the four orderings and arrays under `<=>`; a struct operand declines as before.
- Not built, and filed rather than promised as [#99](https://github.com/portlandlang/portland/issues/99): `sort` with a comparator block (2.4% of gems), `min_by`/`max_by` (0.9%/0.6%), and `min`/`max` with a block.
- Pinned by `spec/struct/comparable_spec.pdx` on both oracles, the value-methods fixture, the seed's unit tests, and the checker's refusal rows. Ledger: [ordering.md](../ruby/ordering.md).
